# 项目分析与开发计划（v4.0 → v5）

> 撰写日期：2026-08-22 · 基线：本地 main（领先远端 v3.2 共 67 个提交，已含 v4.0 全部改动与实测验证）
> 本文档是分析与规划，不改动任何代码。

---

## 1. 项目现状总览

### 1.1 定位与规模

多数据源（arXiv / OpenAlex 期刊 / Hugging Face Papers）每日论文监控与研究趋势分析系统：抓取 → 评分（V2 核心相关性）→ 翻译/TLDR → 可选全文深度分析 → Markdown/HTML 报告 → 多渠道通知，配套 Streamlit 配置面板、SQLite 持久化、WebDAV 同步、Docker 部署。

| 维度 | 数据 |
|---|---|
| 源码 | 74 个 Python 文件，约 29,900 行（src/） |
| 测试 | 25 个测试文件，约 6,400 行；225 个用例 + 58 个子测试全绿 |
| WebUI | 11 个功能 Tab，12 个 tab 模块 |
| 持久化 | 单 SQLite 库 8 张表（运行、论文、精确交付账本、扫描收据/水位线、通知/维护 outbox） |
| 部署 | Worker 384MB / WebUI 785MB 双镜像，cron + trigger watcher 长运行 |

### 1.2 架构分层

```
入口 main.py ─┬─ daily_research（每日研究主管线）
              └─ trend_research（趋势研究管线）
sources/        arxiv / openalex / huggingface + 声明式 source_registry
agents/         analysis（评分/翻译/深度分析）/ keyword / trend + LLM 请求池（RPM 限速）
report/         daily / trend / keyword_trend 三套报告器
notifications/  6 渠道 + 外置模板 + SQLite outbox 指数退避重试
webui/          Streamlit 面板（配置、触发、报告预览、诊断）
utils/          config_io（原子写/EBUSY 回退）、daily_research_store、
                run_lock、webdav_sync、scoring_evaluation、token_counter、updater…
```

### 1.3 质量现状（强项）

- **可靠性设计成熟**：fail-closed 贯穿（坏状态/坏配置/缺收据一律显式失败）；报告落盘后交付、运行完成、通知 outbox、维护任务单事务提交；`(source, canonical_id, version)` 精确交付账本；arXiv v1/v2/v3 独立交付。
- **可观测性已具雏形**：终态扫描收据、水位线推进、运行健康摘要、只读诊断 CLI（`scoring_evaluation diagnose`）。
- **安全边界清晰**：声明式数据源拒绝一切可执行字段；WebUI 只绑 127.0.0.1；密钥不回流浏览器；cron 不再泄漏环境变量；PDF 下载有尺寸/数量防护；报告预览 iframe 隔离 + Markdown 消毒。
- **2026-08-22 实测**：真实触发每日研究，16 天窗口完整抓取 1495 篇原子入队、限量处理 3 篇、报告生成与交付正常、exit 0；同时抓出并修复 3 个真实 bug（页脚版本硬编码、`.env` 挂载保存 EBUSY、保存无关 Tab 改写评分公式）。

## 2. 现存问题清单

### 2.1 确认的 Bug（建议立即修）

| # | 问题 | 位置 | 影响 |
|---|---|---|---|
| B1 | 版本比较用字符串相等判断，**旧版本会被当成新版本**并误发更新通知 | `src/utils/updater.py:238` | 本地 4.0 vs 远端 3.2 时每次运行都提示"发现新版本"；公开后所有领先用户都会遇到 |
| B2 | `time.sleep(1)` 但模块**未 import time** | `src/webui/tabs/trend_runner.py:296` | 非 Docker（本地 subprocess）方式成功启动趋势分析后立即 NameError，页面报错但进程已启动，用户困惑 |
| B3 | WebUI 保存会**丢掉 config.json 全部注释**并重排键序 | `config_io.py` 写入为规范化 JSON | 用户精心注释的配置被静默清洗；对二次阅读和文档化不友好（v3.2 起就存在） |
| B4 | Streamlit `st.tabs` 每次 Run 渲染**全部 11 个 Tab 的控件**（实测页面同时存在 36 个 switch） | `webui/config_panel.py:200` | 每次交互全部 tab 重算，面板变慢、会话状态易串；应改侧边栏导航按需渲染 |

### 2.2 结构性缺口（按用户感知排序）

| # | 缺口 | 现状证据 |
|---|---|---|
| G1 | **无成本/预算控制** | 全代码库无 token 预算、无单次运行花费上限；唯一节流阀是 `max_papers_per_run`。实测后队列积压 1492 篇，恢复 0（全量）后下一次 cron 将一次性调用 LLM 评分+翻译约 1500 篇——花费和时长都不可控，这是当前最真实的用户风险 |
| G2 | **Token 用量不持久、不上面板** | `token_counter.py` 是进程内单例，运行结束即丢；数据只进报告/通知正文，WebUI 的运行历史完全不展示 |
| G3 | **评分反馈闭环断裂** | 已按最终决策处置：反馈闭环不再规划，相关标注/评估代码已从 `scoring_evaluation.py` 移除（保留只读 diagnose 诊断）；其诉求由收藏偏好 + `learned_preference_v1` 学习模式评分承接 |
| G4 | **报告/数据无生命周期管理** | `data/reports/` 无任何清理；日志有 30 天轮转但报告永久累积；SQLite 无 vacuum 策略 |
| G5 | **老用户升级路径空白** | v4 设计决策：旧 JSON 历史不迁移不双写。现有 v3.2 用户升级后历史"清零"（论文可能因无交付账本而重新推送一遍）。公开发版需要显式说明，或提供可选导入器 |
| G6 | **WebDAV 无加密、无远端清理** | 明文上传，只增不删；配额型网盘（坚果云）迟早塞满 |
| G7 | **WebUI 无认证** | 仅靠 127.0.0.1 绑定 + 注释提示上反向代理；没有可选的内建令牌认证 |
| G8 | **趋势模式测试债** | 本轮只验证了每日研究；趋势分析模式（trend_research + trend_runner Tab）没有等价的端到端实测，且恰好藏着 B2 |
| G9 | **语义搜不到自己的报告** | 报告查看页只有文件列表浏览，无按关键词/论文/日期检索 |

## 3. 功能建议（新能力）

按"价值 ÷ 成本"排序，标注依赖关系。

### F1 成本与积压管理（P0，建议 v4.1 核心）

用户最直接痛点：LLM 花费不可见、不可控，积压时一次性爆发。

1. **单次运行预算**：`daily_research.max_tokens_per_run`（0=不限）。评分/翻译/分析前检查累计 token，超预算则剩余论文安全留队（复用现有原子入队语义，天然支持中断续跑）。
2. **积压消化策略**：`max_papers_per_run=0` 且积压 > N（如 200）时，自动按"失败重试 > 最旧优先"分批消化并打日志，替代一次性全量；面板显示"预计还需 X 天消化完"。
3. **Token 用量持久化**：每次运行结束把 per-model 用量写入 SQLite（新表 `run_token_usage`），运行历史与高级诊断展示；按天/月聚合视图。
4. **成本预估**：按历史平均 token/论文 × 队列长度 × 单价（可配置单价表）估算，触发前在面板可见。

依赖：F1.3 是 F1.4 的前置；F1.1 复用 token_counter 现有埋点。

### F2 评分反馈闭环（P0，v5 主打功能）

把已有但断开的能力串起来，这是本项目区别于"RSS 阅读器"的核心竞争力。

1. **报告页内标注**：HTML 报告每篇论文加 👍/👎/跳过（写入 SQLite 新表 `paper_labels`，含标注时间与当时分数快照）；WebUI 报告查看页同步提供列表式标注视图。
2. **一键导出标注** → 直接产出 `scoring_evaluation evaluate` 需要的 JSONL 格式（现有格式已严格校验）。
3. **阈值调优建议**：基于标注跑现有阈值扫描，输出"若门槛从 6.0 → 6.5，F1 变化"，一键应用（写回 config.json 走现有校验链）。
4. （远期）**关键词权重建议**：从 FP/FN 论文的匹配关键词统计，建议权重调整。

依赖：F2.2/2.3 完全复用 `scoring_evaluation.py` 已有函数，成本主要在 UI。

### F3 数据生命周期（P1）

1. 报告保留策略：`reports_retention_days`（默认 180），每日运行尾部清理过期报告（维护任务走现有 maintenance_outbox，可重试）。
2. SQLite 维护：定期 `PRAGMA incremental_vacuum` + 页面统计进高级诊断。
3. 已交付论文元数据压缩归档（保留账本，瘦身 paper_json）。

### F4 订阅与输出渠道（P1）

1. **RSS/Atom Feed**：`data/reports/daily_research/feed.xml` 每次交付后重写，宿主静态文件即可被任何阅读器订阅——零成本新增"通知渠道"。
2. **周报模式**：`weekly_digest` 汇总 7 天及格论文 + 趋势关键词，走现有通知模板系统。
3. （P2）Telegram bot 交互：查看今日报告、标注论文（与 F2 联动）。

### F5 升级与迁移工具（P1，公开发版前完成）

1. `scripts/import_legacy_history.py`：可选地把 v3.2 `*_history.json` 导入交付账本（标记 `imported=true`），防止老用户升级当天被 4 个月旧论文轰炸。
2. 升级文档：CHANGELOG v4 条目补充"影响与迁移"小节。

### F6 WebUI 体验（P1/P2）

1. **按需渲染**（修 B4）：侧边栏 `st.navigation` + `st.Page`，只渲染当前页；顺带解决跨 tab 会话状态污染。
2. **报告检索**（G9）：SQLite 已有全部论文元数据，加一个"论文搜索"页（标题/作者/分数/日期过滤，链接到对应报告）。
3. **内建访问令牌**（G7）：`WEBUI_ACCESS_TOKEN` 非空时启用查询参数/头认证，方便挂到有 TLS 的反代后。
4. 运行历史页展示 token 用量与花费（依赖 F1.3）。

### F7 小而美的修复（P0，随 v4.1 发布）

- B1：semver 解析比较（远端更旧 → "当前已是最新/领先"）。
- B2：补 `import time`。
- B3：注释保留——两个方案任选：① 写入用 JSONC 序列化器（保留注释成本高、易碎）；② 推荐：把注释迁到 `configs/config-reference.md` 文档 + 写入时在文件头生成一行"由 WebUI 管理，说明见 config-reference.md"。
- 更新检查通知去重（同一远端版本只提醒一次，可在 SQLite 记已提醒版本）。

### 明确不做的（2026-08-22 决策）

- **成本控制/预算**（F1）——暂不做；测试阶段用 `max_papers_per_run` 手动限量即可。
- **评分反馈闭环**（F2 原方案）——不做。评分主体是 AI，额外人工反馈输入反而可能放大模型幻觉；评分功能现状可接受。
- **老历史导入器**（F5）——不做。
- **RSS 订阅**（F4）——暂不做。
- **数据保留策略/清理**（F3）——**反转原计划**：数据永不主动删除，全部永久存档（含报告、SQLite、偏好标记——清除偏好也只写 `none` 状态而非删行）。

### v4.0 后续候选（未排期）

- 报告/论文检索页（G9，SQLite 元数据已齐备）。
- WebUI 可选访问令牌（G7）。
- 趋势模式端到端实测（G8 测试债）。
- 周报/摘要类输出（远期）。

### 明确不建议做的（维持原判断）

- 自建用户系统/多租户——单用户工具，收益低。
- 把趋势分析并入每日管线——两者节奏与成本模型不同，保持独立。
- 前端框架重写 Streamlit——侧边栏按页渲染已解决性能问题。

## 5. 风险与依赖

| 风险 | 说明 | 缓解 |
|---|---|---|
| 积压爆发（短期最高优先） | 恢复 `max_papers_per_run=0` 后下一次 cron 全量处理 ~1492 篇 | 当前测试阶段已设上限 3/次；成本控制功能明确不做，靠手动限量 |
| 上游 API 变动 | arXiv/OpenAlex/MinerU 接口变化 | 现有 fail-closed + 收据机制会显式失败；考虑契约测试 |
| LLM 供应商涨价/限流 | 无多供应商容错 | 现有 RPM 池可扩展为多 key 轮换（远期） |
| SQLite 单文件膨胀 | paper_json 全量元数据；数据永不删除 | 接受增长；需要时可加归档表（只搬不删） |
